# GitHub暂态写入异常：先确认远端，再间隔多次安全重试

## 1. Owner原话

> 今后你注意如果一次github仓库写入遇到问题不要立刻就按写入失败处理直接停止工作，可以间隔一会儿多试几次，最近似乎github仓库写入比较容易出问题，但绝对不是没有权限，你在以后给“次一档”模型的任务书中也要求它们多试几次。

本条是MyOS2当前轨道的持续行为要求，不导入Mnemosyne或其它项目维护任务，不改变唯一写区、单写者、非强推和禁止内核运行等边界。
Owner明确确认已有授权不应因一次故障被重新当成缺权限。下列重试次数/间隔是主线给出的执行默认值，不冒充Owner逐字指定参数。

## 2. 不能混为一谈的状态

- 单次工具超时、网络/服务异常、限流、临时写动作未出现在工具列表：尚不能证明仓库没有权限，亦不能证明写入未发生。
- 对目标新文件的预期404，在仓库及固定父提交可读时仅说明该路径未找到，不等于整个仓库访问被拒绝。
- expected-head不匹配或同名文件出现：必须先核远端归属，属于并行/状态一致性问题，不能盲目用旧提交反复覆盖。
- 后端明确的永久认证撤销、策略禁止、写区越权或已确认竞争写入：不得绕过或强推；只停受影响动作，保全已完成工作并继续独立安全项。

遇401/403等返回时先辨别限流、暂态代理错误、仓库状态和真实认证信息；没有充分证据不得写“Owner未授权”。
Owner对现有权限的确认也不构成绕过未来真实安全或认证限制的授权。

## 3. 默认重试节奏

对可重试的暂态故障，通常实行首次尝试加最多三次重试，共四轮；若已确认前次成功、出现真实安全冲突或收到明确永久拒绝，则不凑次数。
默认重试间隔约10、20、40秒；可先继续不依赖该写入的只读核查形成实际间隔，也可在现有临时环境等待。
若服务提供Retry-After或限流重置时间，应遵守服务要求，不以更短间隔密集撞接口。
所有重试均在当前响应执行期间进行，不承诺离线后台继续，也不因等待而启动额外付费服务。

工具列表中临时缺少写动作时，按同样的多轮节奏重新发现相关正规写动作，区分“发现次数”与“实际写请求次数”。
可检查已经连接且明确支持本任务的正规入口；不得用GET动作伪造写请求、搜取凭据或切换到未授权写区。
一轮发现无结果不应立即结束整个工作；不得伪造实际没有调用的写请求或后端拒绝。

## 4. 每轮重试前的远端确认

1. 读取目标分支HEAD及相关目标文件/评论/PR当前状态。先确定前次是否已成功而仅返回丢失。
2. 若目标内容、blob和预期提交已存在，转入后置核验，不再重复创建提交或评论。
3. 若HEAD仍等于预期父提交、目标未完成且写区安全，可重试同一逻辑操作，保持force=false并使用可用expected-head。
4. 若HEAD变化，比较实际增量和归属；已是自己的目标提交则核验，未知并行变化则停该写动作，不强推、不回退、不自动变基。

创建blob/tree/commit已得到真实对象SHA时优先复用；更新ref超时后先查该ref是否已指向目标SHA。
创建提交响应丢失时先检查可见提交/父关系；无法确认身份就记状态未知，不声称出现一个新的正式提交。
添加评论超时后先读最新评论，以任务ID、固定提交和正文标识查重；禁止为了“再试”重复发相同交付。
更新PR正文前后只处理本主线有权维护的导航；执行者仍不能因此修改PR正文或他人评论。
多个不同文件的顺序写入不得假装原子完成；最终以整体净差异和完整回读为交付标准。

## 5. 何时报告阻断

经实际有间隔的多轮恢复仍不可用，才准确报告暂态发布阻断；说明尝试数、异常类别、远端HEAD、已经保存的对象/路径、未完成步骤和最小恢复动作。
不把未知写入结果说成确定失败，不把未发布附件说成已发布任务，不让Owner重复搬运长文件来代替正常GitHub交接。
若只是PR导航/评论暂时失败而正式任务文件已固定入库，应分别说明，保留有效固定入口，不把整个发布状态退回为“什么都没完成”。
既有28号“验收＋后继任务同轮发布”仍有效；重试不是要求Owner再次批准同一已授权步骤。

## 6. 后续任务书必须携带的条款

每份新任务书，特别是给次一档模型的执行任务，必须要求完整读取本63号，并显式写入：
“GitHub暂态异常不因一次失败直接停工；先核远端是否已写成，再按63号间隔重试，通常首次加三次。保持expected-head/force=false；未知并行写入不覆盖。记录实际重试和回读结果，不能把工具缺失推断成没有仓库权限。”

MANIFEST或本人交付评论记录实际write_retry_log：logical_operation、attempt、error_kind、remote_head_before_retry、remote_effect_observed、delay_or_intervening_work、retry_action、final_readback。
没有遇到故障时写not_needed；未尝试不得写已重试。工具重新发现日志与真实写请求日志分开。

本规则只增加故障恢复纪律；不授权修改内核、编译运行、合并/关闭、强推、删分支、新建竞争PR、扩大写区或跨仓维护。
